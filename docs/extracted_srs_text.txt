1. Introduction and Purpose
This document defines the product requirements for a web application used to maintain a voluntarily provided contact directory, organize contacts into three user-managed categories, view contact information, search and filter records, and manage birthday and marriage-anniversary reminders. It provides a common baseline for product owners, developers, testers, and deployment/support teams.
1.1 Intended audience
Project owner / business stakeholder
UI/UX designer
Frontend and backend developers
QA / testing team
Deployment and application-support team
1.2 Requirement language
“Shall” means mandatory. “Should” means recommended. “May” means optional. Features identified as proposed or requiring confirmation are not commitments from the source PDF.
2. Product Scope
The application shall provide a secure, responsive contact-management workspace with:
A dashboard showing total contacts, category counts, upcoming birthdays/anniversaries, and reminders due today.
Three categories: My Confirmed Supporters, Neutral Contacts, and Other Contacts / No Particular Association.
Individual editable contact profiles.
Exactly one reminder notification one calendar day before each saved birthday or marriage anniversary, with no same-day or midnight duplicate.
Name/mobile search; village/city, ward/area, and category filters; upcoming-occasion views.
Contact export to Excel-compatible CSV and/or Excel, backup and restore, and contact correction/deletion.
PIN/password protection, privacy safeguards, voluntary and informed data entry, and Hindi/English support if feasible.
The application is a contact-management tool. It shall not infer, secretly collect, or derive a person’s political views or voting preference. Category 1 is permitted only where the person has identified or self-declared as a confirmed supporter, as stated in the source requirements.

6. Business Rules
A contact must have a unique internal contact ID.
A contact’s category is one of the three approved categories in the MVP.
Only a user-confirmed/self-declared association may be represented by Category 1.
DOB and marriage anniversary are optional; no reminder is scheduled for a missing date.
Reminder date is the previous calendar date in the account’s configured time zone, not simply 24 hours before the event.
Leap-day birthdays and anniversaries require a stakeholder-approved policy for non-leap years (recommended: remind on 28 February; confirm).
Deleting a contact cancels future reminders and removes it from normal search/list views.
The system shall not generate reminders for dates already passed if the previous-day reminder window was missed; the dashboard may show a missed reminder only if the product owner approves that behavior.
7. Reminder Scheduling Specification
This section defines the required behavior; the exact delivery channel and clock time are open decisions.
7.1 Required schedule
On contact create or date change, calculate the next occurrence of the saved occasion.
Calculate the reminder date as one local calendar day before the occasion date.
Schedule one notification for the agreed local reminder time on that reminder date.
Store a unique reminder key such as contact_id + occasion_type + occasion_year.
Before dispatch, check that the key has not already been delivered; mark it delivered atomically after successful dispatch.
Do not schedule a second job for midnight or the occasion date.
When the date changes or contact is deleted, cancel/update pending jobs and invalidate old reminder keys.
7.2 Duplicate prevention
Use a persistent reminder record with status: pending, sent, cancelled, or failed.
Use a database uniqueness constraint on contact_id, occasion_type, occasion_year (or exact occasion date).
The delivery worker shall use an idempotency key so retries do not produce a second user-visible alert.
A retry after a transient failure shall retry the same reminder record, not create a new reminder.
A successful notification shall be recorded with delivered_at and channel/provider response where available.
7.3 Web notification limitation
A browser tab cannot reliably deliver scheduled notifications while closed without a server-side scheduler and a supported push mechanism. For dependable delivery, use a backend scheduler/queue plus Web Push (with service worker and user permission) or another approved channel. Dashboard reminders are available when the user opens the app. Delivery cannot be guaranteed if push permission is denied, the device is offline, or the browser/OS blocks notifications; the UI must communicate this.
7.4 Reminder message examples
“Tomorrow is [Contact Name]’s birthday.”
“Tomorrow is [Contact Name]’s marriage anniversary.”

9. UI / UX Requirements
Clean, simple interface with clear navigation and readable contact lists.
Responsive layout for desktop, tablet, and Android mobile browsers.
Suggested primary navigation: Dashboard, Contacts, Reminders, Backup/Export, Settings.
Contact list should show name, mobile, category, village/city, and next occasion where available.
Contact detail page shall show all saved fields and provide Edit/Delete actions.
Forms shall show field labels, validation messages, save/cancel actions, and unsaved-change warning where appropriate.
Provide empty states (no contacts/no reminders), loading states, and clear success/error feedback.
Hindi and English language support should be designed using localization files rather than hard-coded UI text.
Use accessible contrast, keyboard navigation, visible focus, and semantic labels.
10. Security, Privacy and Compliance Requirements
All production traffic shall use HTTPS/TLS.
Passwords shall be stored using a modern password hashing algorithm (e.g., Argon2id or bcrypt with an appropriate work factor), never plaintext.
Sensitive contact data shall be protected at rest where technically feasible; encryption keys must not be stored beside encrypted data.
Authorization shall ensure each user can access only their own contacts unless an approved sharing model exists.
Validate and sanitize inputs; protect against SQL injection, XSS, CSRF (where applicable), insecure direct object references, and malicious file uploads.
Profile photos shall be type/size validated, stored privately, and served using access-controlled URLs.
Do not place contact names, phone numbers, notes, or dates in application logs, analytics, or error traces unnecessarily.
Provide consent/notice language explaining what data is stored and why; record user acknowledgment if required by product/legal review.
Provide data export, correction, and deletion controls.
Use least-privilege database and hosting credentials; keep secrets in environment/secret management, not source code.
Use security updates, dependency scanning, and periodic backup restore tests.
This is a product-security baseline, not legal advice. The owner should review applicable privacy/data-protection obligations before launch.

12. Technical Architecture Proposal
The source PDF does not prescribe a technology stack. The following is a proposed implementation that can be changed by the project owner.
Layer
Proposed technology / responsibility
Frontend
React + TypeScript; responsive UI; localization; form validation; service worker for web push if approved.
Backend
Node.js + Express/NestJS REST API; authentication; authorization; contact CRUD; export/backup endpoints.
Database
PostgreSQL or MySQL relational database; indexed contact and reminder tables.
Scheduler / queue
Backend scheduled worker/queue for reminder creation and dispatch; idempotent jobs.
Notification
Web Push provider/service worker; fallback dashboard reminders. Email/SMS only if separately approved.
File storage
Private object storage for profile photos and backup files; access-controlled URLs.
Hosting
Managed cloud/VPS with HTTPS, environment secrets, monitoring, and automated backups.
12.1 Suggested high-level flow
Browser UI → HTTPS API → Authentication/authorization → Contact & reminder services → Database. A scheduler reads pending reminder records and dispatches through the approved notification provider. Private photos/backups are stored separately with controlled access.

14.1 Reminder acceptance test must be demonstrated
Before final delivery, the developer shall demonstrate the reminder flow with test contacts and a controlled clock or test scheduler. Evidence should show one previous-day alert, no occasion-day/midnight duplicate, correct cancellation after date edit, and duplicate prevention after worker retry.
15. Error Handling and Operational Requirements
Display clear messages for network failure, validation failure, expired session, backup failure, export failure, and notification permission/status.
Do not display stack traces, database errors, secrets, or contact details in user-facing error messages.
Log system errors with correlation IDs and timestamps; redact personal data.
Provide health checks for backend and scheduler/worker.
Monitor failed reminder jobs and provide a retry/reconciliation process that preserves idempotency.
Document deployment, environment variables, database migration, backup/restore, and rollback steps.
Maintain a support procedure for notification provider outage and data restore.
